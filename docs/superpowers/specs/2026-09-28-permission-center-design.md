# 权限中心设计方案

状态：用户已确认开始实施（2026-09-28）；按后续补充要求完成测试、修复后提交 feature 分支。
基线：`codex/feature-permission-config`，`f531a96`。

## 1. 目标与明确边界

在 Header 的“配置中心”之后新增“权限中心”，统一配置项目空间以外的人员、功能和数据权限。项目空间内的项目角色、计划、资源、转维权限继续由原有项目权限管理。系统超级管理员拥有全系统权限。

用户要求：角色分组可选择或新增且必填；角色名称手输、必填、不能重名；角色定位/范围选填。添加成功后，角色出现在分组树中并自动选中。角色内展示功能分类和菜单树，右侧配置当前菜单的人员、功能与数据权限。项目视图和路标支持筛选条件和可见列配置。保持现有 UI 风格和紧凑间距，完成开发后进行一轮完整测试。

已确认的交互规则：人员按“角色 + 菜单”配置；人员选择、功能勾选和可见列调整即时保存并生效，无需点击保存；两侧树栏尽量窄，并可独立展开、收起。数据筛选条件填写完整并通过校验后自动生效；生效后的筛选与列设置摘要采用用户新参考图的浅紫圆角胶囊标签。多角色建议采用授权并集，但每条授权的数据范围和可见字段保持关联；仅“系统超级管理员”自动拥有全部权限。

当前工程是使用浏览器本地持久化的 Mock 应用。本次实现并验证前端权限行为和本地保存，不将其描述为已具备服务器端鉴权。

## 2. 当前代码与可复用基础

- `AppShell.tsx` 当前主导航为工作台、项目管理、项目组合管理、tOS路标、人力资源管道、配置中心；权限中心容器存在，但未接入主导航和 `page.tsx`。
- `permission.ts` 已有全局角色、全局功能权限、项目角色、持久化迁移、全局和项目权限检查函数。全局角色以名称作为标识，“管理组”目前是角色而非分类，且直接绕过全局和项目权限。
- `GlobalPermissionConfig` 当前为角色表格和功能勾选矩阵，无分组、角色定位/范围、部门、行范围或字段授权。
- 项目配置仍使用 `projectRegistryPermissions.ts` 的指定负责人规则。迁移时必须保留其项目属性和项目类型范围，不能将负责人提升为超级管理员。
- 项目视图已有字段定义、筛选条件和列配置；路标已有表单视图、版本演进视图、品牌等条件和独立列配置。复用实际字段字典，不维护一份脱离页面的中文列名列表。
- 人员候选复用 `projectUserDirectory.ts`。现有部分演示用户具备部门映射，未有部门信息的人员保留个人授权，不推测真实组织归属。
- 当前 UI 合同来自 `docs/prd/全系统UI规范.md`：14px 正文、32px 控件、50px 顶栏、12px 表单行距、16px 列距、6px 控件圆角、现有紫色主色和 Ant Design 图标。

## 3. 方案选择

| 方案 | 优点 | 代价与判断 |
| --- | --- | --- |
| 扩展现有权限 store，新增稳定角色标识、菜单策略和统一计算函数 | 延续现有持久化及调用方式，能覆盖功能与数据权限 | 需要迁移现有角色并逐一接入消费者，推荐 |
| 只改权限配置页面，继续只存角色与布尔开关 | 改动少 | 无法实现按品牌、字段和部门实际限制，不满足需求 |
| 新建独立权限系统，完全替换全局与项目权限 | 模型统一 | 扩大到项目空间权限重构，迁移风险大，超出本次必要范围 |

采用第一种方案。全局权限作为独立清晰的领域实现，项目权限调用保持兼容；统一替换散落的“角色名称等于管理组”判断。

## 4. 页面和交互

### 4.1 三栏结构

```text
Header：…  配置中心  权限中心

角色搜索 / 添加角色       当前角色：名称、分组、定位/范围、编辑
分组与角色树             功能权限菜单树           当前菜单配置
  管理组                   项目管理               人员配置
    系统超级管理员           项目视图             功能权限
    管理员                   项目配置             数据权限
  tOS路标组                项目组合管理             筛选条件
    …                        tOS&整机1+N项目计划     可见列
  项目组                   tOS路标                自动保存状态
    …                        表单视图
                             版本演进图
```

两侧栏采用窄布局：角色栏默认约 180px，功能菜单栏默认约 176px，右栏使用剩余空间。树节点保持紧凑缩进，长角色名、菜单名用单行省略和悬停完整提示，不为少量长名称整体加宽侧栏；完整名称同时保留可访问文本。搜索框和添加入口适应窄栏，不撑宽布局。不引入大标题、营销插图或层层卡片。角色树与菜单树独立滚动，配置区内部滚动；当前菜单标题旁显示轻量自动保存状态，不设置固定保存操作栏。

角色分组侧栏和功能菜单侧栏均支持独立展开、收起，可以同时收起；默认展开。复用系统现有侧栏折叠样式与图标，收起后各保留约 40px 的窄栏和始终可达的 32px 展开按钮，右侧配置区自动占用释放的空间。按钮分别明确标识“展开/收起角色侧栏”和“展开/收起菜单侧栏”，支持键盘操作、提示和 `aria-expanded` 状态。

侧栏折叠仅改变布局，不改变当前角色、当前菜单、树节点展开状态、搜索内容和未填完整的筛选条件，不触发离开确认。再次展开恢复原状态；本次页面会话内切换角色和菜单不重置两栏的折叠状态。分组树节点自身的展开/收起与整栏折叠互不影响。新增角色成功时自动展开角色侧栏及目标分组，保证新角色的选中反馈可见；保留功能菜单侧栏的折叠状态。

窄屏将两棵树折叠为可打开的选择入口，避免两个窄栏挤占配置区；选中角色或菜单后收起对应选择面板，保留全部配置能力。未完成的条件编辑仍遵循下文的离开保护。

点击分组只展开或收起；点击角色加载该角色，默认选中上次菜单或首个可配置菜单。角色与菜单支持搜索。无结果和未选择菜单均显示明确空态。

### 4.2 添加和维护角色

“添加角色”弹窗按以下顺序展示：

1. 分组：必填，可搜索下拉；没有匹配项时，在下拉内输入并添加新分组。一次只选择一个分组。
2. 角色名称：必填，去除首尾空白后全局查重；规范化全角字符及英文大小写用于查重，展示保留用户输入的合理格式。
3. 角色定位/范围：非必填，多行文本。

点击“添加”先校验，再一次性写入分组和角色；取消不会残留空分组。成功后关闭弹窗、展开目标分组并选中新角色。新角色没有任何有效授权；配置人员和权限时逐次即时生效，无需额外保存。

普通角色支持编辑名称、分组、定位/范围及删除。使用稳定 ID 关联授权，重命名不丢失权限。删除前明确提示会撤销该角色授权；删除选中角色后选择同组相邻角色或首个剩余角色。

### 4.3 当前菜单的人员配置

右侧“人员配置”对应当前角色的当前菜单。多选器支持按姓名或部门搜索，选项分为“人员”和“部门”，已选对象以可删除标签展示。选择或移除对象后即时保存并重算授权。个人与部门去重，选中部门后根据组织映射计算其成员，不复制一份静态人员名单。

没有部门映射的人员仍可按姓名选择。部门授权仅使用已有可验证的演示组织数据；不接入飞书通讯录，也不虚构真实员工的部门关系。空人员列表意味着该菜单策略不会授权给任何人。

系统超级管理员的人员在角色层维护，因为其授权覆盖所有菜单；右侧各菜单统一显示全部权限，不能单独取消。阻止删除内置超管角色或移除最后一位有效超级管理员。

### 4.4 功能权限

按当前菜单真实存在的操作显示“查看、导出、导入、新增、编辑、删除”等复选项；保留配置中心原有编辑和发布粒度，路标原有基线和分享粒度不丢失。不存在的操作不显示空开关。

勾选其他操作时自动勾选“查看”；取消“查看”时同步取消该菜单依赖查看的操作。一次操作连同依赖变更原子保存并立即生效，避免中间授权状态。未授权时，导航和菜单不出现；通过状态切换、旧链接或旧弹窗进入也必须在执行处校验。

### 4.5 数据权限

数据权限分为“可见数据”和“可见列”。

- 可见数据：选择“全部数据”或“符合筛选条件的数据”。条件支持字段、运算符、值，支持“满足所有条件 / 满足任一条件”，字段和候选值来自目标菜单的实际定义。
- 品牌限制示例：字段为“品牌”，运算符为“等于”，值从实际品牌枚举中选择。参考图的 TECNO、Infinix、itel 作为业务示例；当前 Mock 品牌是示例品牌，不静默修改演示数据集。
- 条件模式下必须有完整有效条件，完整后自动写入并生效。缺失字段、运算符不匹配、值未填写时显示“条件未完整，尚未生效”，继续使用上一份有效策略；首次新增策略仍无授权。切换条件模式及新增、编辑、删除条件按一份完整策略校验，移除最后一个条件不会隐式变成全部数据。运行时遇到非法或未知字段不能退化为全部数据。
- 可见列：支持搜索、全选、清空可选列和逐项勾选，勾选后即时生效。选择“指定列”时至少选择一列；对视图必要的识别字段明确标注并保护，拒绝会导致视图无法正常呈现的操作并给出提示。
- 授权允许列与用户个人列设置取交集；用户在页面重新全选列也不能恢复未授权列。跨角色对不同行拥有不同字段授权时，按行处理隐藏字段，不能将两个角色的行、列任意交叉组合。
- 对没有结构化行列的菜单不展示无意义的数据配置。项目视图和两个路标视图必须支持行条件与字段配置，并覆盖对应详情、卡片、演进图标签、统计和导出内容。

筛选与列设置的生效态摘要遵循用户提供的“品牌 包含 tecno”标签参考图：

- 使用约 32px 高的圆角胶囊、浅紫底、细浅紫边框；字段名采用现有紫色主色和中等字重，运算符用次级灰色，值用正文深色。右侧使用图标库的红色圆形关闭图标；视觉小图标保留足够的按钮点击区域、键盘焦点和明确名称。
- 每条筛选以“字段名 + 运算符 + 值”显示，例如参考图的“品牌 包含 tecno”；示例仅约束呈现方式，实际值仍来自当前菜单数据。点击标签正文打开该条件的编辑浮层，点击关闭只移除对应条件，不连带触发编辑浮层。
- 已选可见列使用同一胶囊样式，列名使用紫色强调，右侧关闭图标取消该列授权并即时生效；受保护的必要识别列显示不可移除状态及原因。点击“列设置”打开紧凑选择浮层，勾选结果同步更新标签。
- 多标签以约 6px 间距紧凑换行；长字段值省略并提供完整提示，关闭按钮始终可见，不因文本超长被挤出。保持原有字号和对比度，不照抄低对比度像素值。
- 标签与底层生效策略保持一致，仅展示已生效内容。条件未完整或变更失败时显示对应内联提示，不能让标签暗示无效配置已经生效。移除最后一个筛选条件或必要列仍遵循前述有效性校验，不隐式放开全部数据。

这里的“保存样式”指实时生效后的标签展示，不新增手动保存按钮。

### 4.6 即时生效与未完成输入保护

不显示“保存”或“取消修改”按钮。人员、部门、功能和可见列的每次有效变更原子写入 store 和浏览器本地存储，立即重算相关权限；筛选条件完整有效时自动提交。需要撤销已生效的勾选时直接反向勾选，不存在待整体提交的权限草稿。

菜单标题旁轻量显示“已自动保存”；写入失败显示内联错误，保留上次有效配置并提供重试，不伪报已生效。快速连续勾选按最新值合并，避免旧值覆盖新值。即时写入失败不扩大权限。

已自动生效的配置在切换角色、菜单、主导航和测试身份时无需离开确认。只有尚未完整、尚未生效的筛选条件输入或未提交的角色表单需要离开保护；提示明确说明未完成内容，复用既有编辑保护机制。侧栏展开、收起不触发离开。

每次变更成功后立即更新当前用户可见入口、操作和数据。若当前页面或已打开的详情不再有权限，清理原有选中和缓存展示，落到仍可访问的入口；没有入口时展示无权限状态。移除自己的普通权限时同样即时生效；最后一个超级管理员保护在写入前完成。

## 6. 权限生效规则

### 6.1 完整授权单元

每条授权包含：角色 ID、菜单 ID、人员/部门对象、功能集合、数据条件和可见字段。条件与字段均使用稳定键而不是展示名称。

单条策略内：人员命中且拥有目标操作且数据条件满足时才授权。多个匹配角色之间取授权并集，但保留每条策略的行、列和操作关联。

例如：角色 A 可导出品牌 A 的项目名称，角色 B 只可查看品牌 B 的成本。用户同时拥有两个角色时，不能因此导出品牌 B，也不能看到品牌 A 的成本。

### 6.2 普通筛选与权限筛选

先得到授权数据集，再叠加页面个人筛选。清空页面筛选只恢复授权范围内的数据。排序、搜索候选、分页总数、聚合统计、导出、详情和演进图共用相同授权来源，不能从未过滤的 store 数据重新生成。

导出按“导出”操作单独计算范围，复用项目既有 `exportExcel.ts`。业务修改在 handler/store 执行前重新校验，不能只依赖按钮禁用状态。配置中心等不能按记录拆分的全局操作仅接受该操作的整体授权。

### 6.3 超级管理员

使用固定内置角色标识判断超级管理员，名称“管理组”仅用于分类展示；自行新增同名相似角色不能获得超管能力。“管理组”下普通“管理员”仍按所配权限执行。

超级管理员权限始终全开并覆盖未来注册的菜单。沿用当前超级管理员能够访问项目空间的既有行为。普通全局角色授权不会自动授予项目空间成员、计划或资源权限。

### 6.4 权限中心自身管理

权限中心管理操作在入口、界面和 store 提交三处校验。普通用户不得通过界面或遗留组件修改角色。只有系统超级管理员可以分配超级管理员身份，普通权限管理员不能借角色编辑将自己提升为超级管理员。

## 7. 存储和迁移

- 新模型包含角色分组、稳定角色 ID、定位/范围、菜单策略和版本化持久化结构。
- 现有全局“管理组”成员迁入“管理组 / 系统超级管理员”，不丢失成员，不授予其他分组同等能力。
- “编辑组”“查看组”和自定义全局角色保留原有有效授权，迁入兼容分组或匹配的角色目录；不得用新默认模板覆盖用户已保存配置。
- 项目配置中原有指定负责人转换为带项目属性、类型条件的明确授权，保持现有可管理范围。
- 对历史上没有全局控制的已存在入口，用明确的兼容策略保存原有访问行为；所有新建角色默认无授权。迁移结果必须可在权限中心看见和调整，不保留隐蔽的永久放行分支。
- 项目级角色、权限、资源版本和业务数据保持不变。旧全局权限键经兼容适配映射到新菜单策略，逐一核对现有消费者。
- 页面刷新后正确恢复分组、角色、成员、条件、列和功能配置；迁移幂等。坏数据报可理解的错误，不能静默扩大授权。

## 8. 实现边界

保持 `permission.ts` 对外兼容，新增独立全局权限类型、菜单目录、纯计算函数及权限中心组件。拆分角色树、菜单树、角色表单、人员选择器和数据策略编辑器，避免继续扩大 `PermissionModule.tsx`。

主要接入点：`ui.ts`、`AppShell.tsx`、`page.tsx`、`GlobalPermissionContainer.tsx`、项目管理与项目视图、项目组合计划、路标、配置中心、人力资源入口，以及现有独立模板和分享页面的对应访问边界。

分享页面不把权限范围序列化为可绕过当前用户授权的通行证。当前用户通过链接访问仍进行权限判断。

样式优先复用全局 token 与现有控件，仅新增权限中心专属布局样式，不安装第二套设计系统。两栏折叠复用 `CollapsibleWorkspace.tsx` 的侧栏组件与交互，两栏折叠状态独立管理，并区分各自的可访问名称。
