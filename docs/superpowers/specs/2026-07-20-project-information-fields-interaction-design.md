# 新增项目与项目空间基础信息迭代设计

## 1. 背景与目标

当前工作台“新增项目”只填写项目名、项目类型和项目责任人；项目空间的基础信息由 `ProjectSpaceContainer` 分类型硬编码展示，新增与编辑不是同一套表单，整机市场信息也仍使用横向表格编辑。

本次迭代以飞书文档 [PMS系统单项目空间设计V0.1](https://transsioner.feishu.cn/wiki/Lwprw9vqKiLiDJkn05NcAUTEnLf) 2026-07-20 读取到的 revision 2811 为字段口径，完成以下目标：

1. 整机产品项目和 tOS 版本项目在创建时填写各自完整字段，并依据“是否创建时必填”校验。
2. 项目空间编辑复用创建表单，打开时回填现有值。
3. 项目空间增加“核心板块”，基础信息按文档分组折叠展示。
4. 支持按用户、项目、信息分组持久化字段显示偏好。
5. 扩充整机市场计划信息和市场编辑字段，市场编辑改为纵向表单。
6. 保留现有权限、编辑保护、整机市场计划隔离和 tOS 类型计划隔离能力。

## 2. 已确认的产品决策

- 整机产品项目使用“基础信息 / 扩展信息 / 团队信息”三组，不再把扩展信息拆成参数和维护两组。
- 文档中标注“二期开发”的整机团队信息在本次直接实现。
- “项目责任人”和 tOS 团队中的“版本项目经理”是两个独立字段：项目责任人用于项目可见范围和系统管理员权限，版本项目经理是业务角色，二者不自动同步。
- 正式环境把字段显示偏好保存到数据库；当前 mock 通过 `localStorage` 实现相同的用户、项目、分组隔离契约。
- 只有整机产品项目和 tOS 版本项目展开完整字段。独立软件产品项目、技术项目和能力建设项目暂时保留现有三字段创建流程。
- “整机 PD、PCBA 表、出货国家表、关键器件选型表”在当前 mock 中使用“链接或 Excel 文件地址”文本输入，不实现真实文件上传。
- 采用 Schema 驱动方案：创建、编辑、展示和校验共享一份字段定义，不在不同组件中重复维护字段清单。

## 3. 范围

### 3.1 本次包含

- 工作台新增项目 Modal。
- 整机产品项目和 tOS 版本项目的项目空间基础信息页。
- 整机市场计划信息展示和市场编辑 Modal。
- 字段显示偏好 mock 持久化及正式存储接口契约。
- 既有 mock 项目字段补齐和兼容映射。
- 与本次交互相关的规则脚本、类型检查、构建和浏览器烟测。

### 3.2 本次不包含

- 真实 IPM、SPUG、SCM 接口接入。
- 字段显示偏好数据库表、后端接口或鉴权实现。
- Excel 文件真实上传、解析和下载。
- 独立软件产品、技术、能力建设项目的完整字段表单。
- 飞书字段文档或本地 PRD 的同步修改。
- 变更 Full、Slim、GO、PAD 的 tOS 类型计划数据模型。

## 4. 总体方案

### 4.1 共享字段 Schema

新增 `src/constants/projectInfoSchema.ts`，为字段定义统一元数据：

```ts
type ProjectInfoGroupKey = 'basic' | 'extended' | 'team'

type ProjectInfoInputType =
  | 'text'
  | 'textarea'
  | 'select'
  | 'multi-select'
  | 'person'
  | 'multi-person'
  | 'date'
  | 'link'
  | 'jira-projects'
  | 'readonly'

interface ProjectInfoFieldDefinition {
  key: string
  label: string
  projectType: '整机产品项目' | 'tOS版本项目'
  group: ProjectInfoGroupKey
  inputType: ProjectInfoInputType
  options?: Array<{ label: string; value: string }>
  required: boolean
  requiredOnCreate: boolean
  autoSourced: boolean
  defaultVisible: boolean
  hideable: boolean
  visibleWhen?: (values: ProjectInfoValues) => boolean
}
```

创建表单、编辑表单、折叠分组、字段配置器和规则脚本都从该 Schema 派生。字段顺序与文档顺序一致。

### 4.2 组件边界

- `ProjectInfoModal`：纯表单组件，支持 `create` 和 `edit` 两种模式，只负责展示、回填、校验并返回结构化值。
- `AddProjectModal`：继续负责候选项目过滤、创建项目、初始化项目成员和权限、进入项目空间；内部复用 `ProjectInfoModal`。
- `ProjectInfoSections`：负责核心板块及可折叠信息分组展示。
- `ProjectInfoSection`：负责单个分组标题、有效字段数、折叠内容和字段配置入口。
- `FieldVisibilityPicker`：负责固定字段和可隐藏字段的勾选状态。
- `MarketEditorModal`：负责市场列表、主市场/跟随规则和市场属性的纵向编辑。
- `projectInfoRules`：承载默认显示、条件字段、创建校验、tOS 聚合和兼容字段同步等纯函数。
- `projectFieldPreferenceRepository`：隔离 mock `localStorage` 与未来数据库接口。

`ProjectSpaceContainer` 只保留权限判断、选中项目/市场状态和保存回调，不继续内联全部字段 UI。

### 4.3 项目数据结构

项目新增通用扩展字段容器：

```ts
type ProjectInfoValue = string | string[] | boolean | null | JiraProjectConfig[]
type ProjectInfoValues = Record<string, ProjectInfoValue>

interface ProjectInfoExtension {
  fieldValues?: ProjectInfoValues
}
```

新字段写入 `fieldValues`，避免继续在项目根对象上堆叠大量仅基础信息页使用的属性。为兼容已有消费者，保存时同时同步以下现有字段：

- `status`
- `healthStatus`
- `currentNode`
- `brand`
- `productLine`
- `productSeries`
- `tosVersion`
- `versionType`
- `developMode`
- `chipPlatform`
- `spm`
- `versionFiveRoles`
- `jiraProjects`

`developmentMode` 同步到旧字段 `developMode`，新的 `researchMode` 独立保存。tOS 团队角色完整保存在 `fieldValues.tosTeamRoles`，同时按以下关系同步现有五大员结构：规划代表 → 版本规划代表、版本项目经理 → 版本经理、SE → 版本 SE、测试代表 → 版本测试代表、SQA → 版本质量代表。整机团队中的 SPM 同步到旧根字段 `spm`，其余角色保存在 `fieldValues.machineTeamRoles`。

读取既有项目时先读 `fieldValues`，缺失则通过兼容映射读取旧根字段。这样无需一次性重写工作台、路标、计划和转维模块。

## 6. 新增与编辑交互

### 6.1 新增模式

Modal 宽度使用适合双列表单的桌面宽度，内容区可滚动，底部操作区固定。顶部通用字段为：

1. 项目名
2. 项目类型
3. 项目责任人

项目责任人必须手动选择，绝不从 SPM 或版本项目经理自动回填。提交成功后仍将责任人写入项目成员可见范围，并初始化为该项目的“系统管理员”。

选择整机产品项目或 tOS 版本项目后，在通用字段下展示核心字段和对应信息分组。表单分组默认展开，便于完整录入；项目空间中的展示分组默认折叠。

切换项目类型时：

- 尚未填写类型专属字段时直接切换。
- 已填写类型专属字段时弹出确认，确认后清空旧类型字段，取消则恢复原类型。
- 自动获取字段在选择项目名后回填并保持只读。

独立软件产品、技术和能力建设项目选择后不出现扩展分组，继续使用现有三字段创建逻辑。

### 6.2 编辑模式

项目空间的“编辑”按钮打开同一个 `ProjectInfoModal`：

- 项目名和项目类型锁定，避免破坏外部项目映射和类型专属数据。
- 项目责任人及全部业务字段回填并可按权限编辑。
- 自动获取字段保持只读。
- 项目责任人变化时同步更新项目成员映射和项目“系统管理员”成员。
- 取消关闭不修改项目；表单被修改后关闭或导航时要求确认放弃。
- 保存采用一次性提交，成功后同时更新项目列表中的对象和当前选中项目。

项目业务字段编辑和市场编辑继续由 `basicInfo:编辑` 控制。无权限用户只能查看项目数据，不能打开编辑或市场编辑 Modal。字段显示偏好属于个人查看习惯，不修改项目业务数据，因此拥有 `basicInfo:查看` 的用户均可配置自己的显示字段。

### 6.3 校验与错误反馈

- 提交时依据当前项目类型和有效条件字段生成校验规则。
- 如果错误字段位于折叠分组，自动展开第一个错误分组并滚动到字段。
- 已填写内容不因校验失败丢失。
- 条件由“是”切换为“否”或条件不再成立时，清空已失效的日期/条件字段值。
- 自动聚合必填字段缺失时，错误消息列出缺失字段和来源项目，不能让用户在只读框内修补派生结果。

## 7. 项目空间展示

### 7.1 核心板块

沿用现有紫色玻璃态主题和 Card 体系，使用响应式信息卡网格，不照搬参考图颜色。核心板块字段多于一行时自动换行，窄屏下减少列数。

页面右侧锚点改为：

- 核心板块
- 基本信息
- 转维信息（整机且存在转维申请时）
- 计划与配置（整机）或计划信息（其他类型）
- 配置信息（适用类型）

### 7.2 可折叠信息组

每个信息组单独使用 Collapse/Card：

- 初始化默认折叠。
- 标题左侧显示图标和分组名称。
- 标题旁显示当前有效且实际展示的字段数，例如“9 项”。
- 标题行右侧显示“配置字段”入口。
- 普通值使用响应式 Descriptions 网格；人员字段使用角色卡片。
- 空值统一显示 `-`。

### 7.3 字段显示配置

配置面板按 Schema 顺序列出该分组字段：

- `hideable=false`：始终勾选、禁用操作。
- `hideable=true`：允许勾选/取消。
- 条件字段即使当前条件不成立也保留配置项，并说明“满足条件时显示”。
- 勾选变化立即更新页面并持久化，无额外保存按钮。
- 首次进入或无有效偏好时使用 `defaultVisible`。
- Schema 增加新字段时，已保存偏好保留已知字段选择，同时自动加入新增的固定字段和默认显示字段。

## 8. 字段显示偏好存储

### 8.1 正式存储契约

偏好记录至少包含：

```ts
interface ProjectFieldVisibilityPreference {
  userId: string
  projectId: string
  groupKey: ProjectInfoGroupKey
  visibleFieldKeys: string[]
  schemaVersion: number
  updatedAt: string
}
```

唯一约束为 `userId + projectId + groupKey`。正式实现由数据库和服务接口负责，前端只依赖 Repository：

```ts
interface ProjectFieldPreferenceRepository {
  get(userId: string, projectId: string, groupKey: string): Promise<ProjectFieldVisibilityPreference | null>
  save(preference: ProjectFieldVisibilityPreference): Promise<void>
}
```

### 8.2 Mock 存储

当前使用 `localStorage`，键格式为：

```text
pms:project-field-visibility:v1:<mock-user-name>:<project-id>:<group-key>
```

行为要求：

- 切换项目、重新进入和刷新页面后保留选择。
- 不同用户、项目和分组互不影响。
- JSON 损坏或字段键已失效时忽略无效项并回落到 Schema 默认值。
- 保存失败时回滚本次勾选并提示“字段显示配置保存失败”。
- 清除浏览器数据后恢复默认值，符合 mock 环境限制。

## 10. 权限与兼容性

- 工作台“新增项目”入口仍只对全局管理组显示。
- 项目空间业务字段编辑和市场编辑由 `basicInfo:编辑` 控制；个人字段显示配置只要求 `basicInfo:查看`。
- 项目空间查看入口及内容继续遵循现有数据权限。
- 表单打开期间的导航必须经过现有 `navigateWithEditGuard`；Modal 自身关闭使用表单 touched 状态确认。
- 离开项目空间仍重置转维子视图。
- 不修改整机按市场隔离计划的 key、版本或跟随逻辑。
- 不修改 tOS 按 Full/Slim/GO/PAD 隔离计划的 key、版本、类型编辑和主类型逻辑。
- tOS 新建项目继续初始化唯一默认主类型 Full，并同时写入 `versionType='Full'` 和 `versionTypes=['Full']`；后续类型增删和主类型调整继续使用已有“类型编辑”。
