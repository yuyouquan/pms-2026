# 三级计划跟随范围实际时间覆盖设计

## 1. 背景与目标

三级计划的跟随市场或跟随类型当前直接读取主市场或主类型的数据，并将整个活动表视为只读。业务确认后的新口径是：计划结构及普通活动字段继续跟随，但跟随范围可以按二级活动维护自己的实际开始时间和实际完成时间。

本设计补充并覆盖《项目空间三级计划设计》中“跟随范围内所有写操作均禁用”的旧约束。除实际时间覆盖能力外，原三级计划的两级活动、权限、排序、删除、工具栏和跟随态界面规则保持不变。

## 2. 最终业务规则

- 整机产品项目的跟随市场默认读取主市场的实际开始时间和实际完成时间。
- tOS 版本项目的跟随类型默认读取主类型的实际开始时间和实际完成时间。
- 有活动编辑权限的人员可在跟随范围内直接修改二级活动的实际开始时间或实际完成时间。
- 一级活动的实际时间仍为聚合结果，不能直接修改。
- 某条二级活动首次修改任一实际时间时，将该任务当前显示的实际开始时间和实际完成时间一起复制到当前跟随范围，并标记为该任务已脱离实际时间跟随。
- 首次修改后，即使只修改了一个字段，该任务的两个实际时间都以当前跟随范围保存的值为准，后续不再接受主市场或主类型对这两个字段的更新。
- 未发生实际时间修改的任务继续实时跟随源范围。
- 清空任一实际时间同样属于修改：目标字段保存为空，另一个字段按首次修改时的当前显示值一起冻结。
- 跟随范围脱离整体跟随后，保留当前显示的全部活动数据、已经覆盖的实际时间及其修改历史，并可继续独立编辑。

## 3. 方案选择

采用“跟随范围实际时间覆盖层”。活动主体仍只保存于主范围；跟随范围仅保存发生过实际时间修改的任务快照。

不采用复制整份活动并持续同步的方案，因为它需要在主范围每次编辑、删除和拖动时判断哪些字段可同步，容易产生部分同步和顺序漂移。也不把市场或类型数据嵌入主活动，因为这会让活动模型与范围数量耦合。

## 4. 数据模型

### 4.1 覆盖记录

按跟随范围自己的稳定范围键保存覆盖记录：

```text
projectId + scopeType + selectedScopeValue + activityId
```

每条覆盖记录包含：

- `activityId`：源范围活动的稳定 ID。
- `actualStartDate`：当前跟随范围冻结的实际开始时间，可为空。
- `actualEndDate`：当前跟随范围冻结的实际完成时间，可为空。
- `detachedBy`：首次建立或最后修改覆盖记录的人员。
- `detachedAt`：最后修改时间。

覆盖记录存在即表示该任务的两个实际时间均已脱离时间跟随，不再需要额外的字段级标记。

### 4.2 存储边界

- `activitiesByScope[sourceScopeKey]` 继续保存主范围活动。
- `actualOverridesByScope[selectedScopeKey][activityId]` 保存跟随范围实际时间覆盖。
- 跟随范围的实际时间修改历史写入 `historyByScope[selectedScopeKey]`，不得污染主范围历史。
- 普通独立范围不创建覆盖记录，继续直接修改自身活动。

## 5. 数据解析与聚合

展示跟随范围时按以下顺序生成最终活动数据：

1. 从解析后的 `sourceScopeKey` 读取主范围活动。
2. 以活动稳定 ID 查找当前 `selectedScopeKey` 的覆盖记录。
3. 有覆盖记录时，用其中两个实际时间替换源活动的对应字段；无覆盖记录时保留源值。
4. 使用合并后的二级活动重新计算一级活动实际开始时间、实际完成时间和实际工期。
5. 表格、筛选、导出和历史上下文统一使用合并后的显示数据。

因此：源范围后续修改实际时间时，未覆盖任务立即更新；已覆盖任务保持本范围值；一级活动聚合也随当前范围最终显示值变化。

## 6. 编辑流程

### 6.1 跟随范围首次修改

用户修改某个二级活动的任一实际时间时：

1. 校验用户对该活动拥有编辑权限。
2. 读取该任务当前显示的实际开始时间和实际完成时间。
3. 以两个当前显示值创建覆盖快照。
4. 将用户本次修改应用到目标字段。
5. 校验修改后的实际开始时间不得晚于实际完成时间。
6. 保存覆盖记录，并在当前跟随范围写入字段级历史记录。

### 6.2 后续修改

如果覆盖记录已经存在，直接在该记录上修改目标字段。另一个实际时间继续使用已冻结值，不再重新读取源范围。

### 6.3 普通独立范围

主范围或非跟随范围维持现有逻辑：有权限人员直接修改二级活动自身的实际时间，并记录活动编辑历史。

## 7. 权限与界面

- 跟随范围仍不显示跟随提示条。
- 跟随范围仍不显示“新增活动”按钮。
- 跟随范围仍不显示活动编辑、新增、删除和拖动入口。
- 二级活动的实际开始时间和实际完成时间是跟随范围唯一开放的写入口。
- SPM、管理员、一级活动责任人及该二级活动责任人沿用现有活动编辑权限，可以修改实际时间。
- 无权限用户看到最终时间值，但不显示表格内编辑控件。
- 修改日期时沿用现有日期选择器和开始时间不得晚于完成时间的限制。

## 8. 脱离整体跟随

市场或类型从跟随变为独立时：

1. 读取当前源范围活动。
2. 合并当前跟随范围的实际时间覆盖，得到用户脱离前看到的完整活动数据。
3. 将合并后的活动复制为目标独立范围活动。
4. 合并源范围历史与当前跟随范围历史，保留原有跟随记录和本范围实际时间修改记录。
5. 保留目标范围已有列设置。
6. 成功物化后清理该范围的覆盖记录；后续直接编辑独立活动。

脱离操作不得把当前跟随范围的实际时间反向写回主市场或主类型。

## 9. 边界处理

- 源范围删除活动后，对应覆盖记录暂不展示，也不影响其他活动；脱离时只物化源范围仍存在的活动。
- 源范围新增活动后，新任务没有覆盖记录，因此自动跟随其实际时间。
- 源活动改名、调整责任人或拖动时，跟随范围继续按稳定活动 ID 应用已有实际时间覆盖。
- 若源活动两个实际时间均为空，用户首次填写一个字段时，另一个字段冻结为空。
- 覆盖记录只控制实际开始时间和实际完成时间；计划时间、状态、风险、责任人和关键节点继续实时跟随。

## 10. 验证方案

### 10.1 自动规则验证

- 无覆盖记录时，跟随范围展示源范围两个实际时间。
- 首次修改实际开始时间时，同时冻结当前实际完成时间。
- 首次修改实际完成时间时，同时冻结当前实际开始时间。
- 首次清空任一字段时仍创建覆盖记录。
- 源范围后续修改两个实际时间时，已覆盖任务保持不变，未覆盖任务继续更新。
- 一级活动从合并后的二级活动聚合最早实际开始时间和最晚实际完成时间。
- 无权限用户不能创建或修改覆盖记录。
- 脱离整体跟随后，独立活动保留覆盖值及历史记录。

### 10.2 浏览器验证

- 在主市场或主类型填写二级活动两个实际时间。
- 切换到跟随范围，确认默认展示相同值且没有新增、编辑、删除入口。
- 修改跟随范围某任务的一个实际时间，确认另一个值一起冻结。
- 返回源范围再次修改两个时间，再切回跟随范围，确认该任务两个时间均未变化。
- 选择另一条未覆盖任务，确认其时间仍随源范围变化。
- 脱离整体跟随，确认活动和覆盖时间保留且可以继续独立编辑。
- 使用无权限用户确认实际时间只读。
- 检查浏览器控制台无新增错误。

## 11. 发布要求

完成实现后依次执行三级计划规则验证、全量类型检查、计划工作台集成校验、生产构建和浏览器验证。验证通过后推送 `dev`，合并并推送 `master`，发布到现有 Vercel 生产项目并验证正式域名。
