# 角色权限配置模板与团队权限合并设计

状态：用户已确认，进入实施。包含四类 Mock 数据、完整权限流程测试及 feature 分支推送。

## 目标与已确认规则

在配置中心按项目类型维护 IPM → PMS 角色映射及初始功能权限；项目空间统一为“团队&权限”，在同一角色列表维护同步角色与本地角色；所有功能权限层级提供批量授权入口。

用户已确认：IPM 成员按同步角色的功能权限生效，额外角色仍不能提升其权限。这取代之前“IPM 团队成员固定只读”的授权规则。仍使用本地 Mock，不连接真实 IPM，不复制截图中的真实人员资料。

全局权限中心与项目空间权限保持独立；只有固定系统超级管理员拥有全系统权限。保持现有 PMS 紫色主题、紧凑间距、窄侧栏、展开收起及人员/部门选择弹窗。

## 1. 配置中心：角色权限配置模板

导航新增“角色权限配置模板”，下设四个独立项目类型：

1. 整机产品项目
2. tOS版本项目
3. 技术项目
4. 能力建设项目

每类项目展示映射表，列顺序固定为：角色名称、IPM角色编码、PMS角色名称、PMS角色编码、操作。示例映射为 `SPM / RJPM / SPM / SPM`。

- 支持添加、编辑和删除映射；四项均必填，去除首尾空格。同一项目类型内 IPM 角色编码、PMS 角色编码分别唯一；不同项目类型可以使用相同编码。
- 行操作包含“配置权限”。点击后打开带角色名、项目类型的 Modal，复用项目空间现有功能权限组件、菜单层级、搜索、折叠及操作名称。
- 模板只包含该项目类型实际支持的功能，不配置人员、部门或数据权限。项目空间还要按项目属性（正式、预算、路标）限制可配置功能。
- 勾选、取消和节点批量操作立即保存模板，弹窗使用关闭/完成入口，不引入额外保存步骤。映射基础字段按完整一行校验后提交，不能存储半条映射。
- 四类模板分别保存。Mock 默认权限为相应可用菜单的查看权限；管理员可以调整初始化的功能权限。
- 每个项目类型的模板入口加入全局权限目录，以“查看/编辑”分别控制访问和修改；没有对应编辑权限时映射及 Modal 均只读。

### 初始化语义

采用“模板初始化项目副本”：项目首次同步某角色时，将当时模板的功能权限复制到该项目角色；之后在项目空间单独调整。

更新模板不追溯覆盖已有项目角色；重新打开页面、刷新团队、重新载入缓存均不能重置项目权限。再次同步只更新成员和来源信息。删除模板也不删除项目中的同步角色或已有项目权限。

没有匹配模板的 IPM 角色仍显示，标识“未配置模板”，以该类型可用的查看权限初始化；后续由项目管理员配置。源角色通过 IPM 编码匹配，不能仅凭名称误匹配。

本轮先采用一对一映射；多条 IPM 编码映射至同一 PMS 编码不属于本轮范围。

## 2. 项目空间：团队&权限

删除独立“团队”导航，将“权限配置”更名为“团队&权限”。原团队导航状态归一到新入口，不能落入空白页。技术子项目继续使用父项目权限作用域。

左侧默认选中首个 IPM 同步角色，支持搜索、分组和整体展开/收起，保持窄侧栏。角色来源用清晰标签区分，不能仅凭同名判断来源。

| 角色来源 | Tab 顺序 | 成员维护 | 删除 |
| --- | --- | --- | --- |
| IPM 同步角色 | 功能权限 → 人员列表 | 展示同步数据，不提供本地增删或部门授权 | 不允许 |
| 本地角色 | 功能权限 → 人员配置 | 保留现有授权人员、授权部门的 Modal 交互 | 允许 |

首次进入及切换角色默认展示“功能权限”。本地角色新增后自动选中，新角色初始权限不继承同名同步角色。

同步角色的“人员列表”按图二列顺序显示：`No. / 成员名称 / 工号 / 角色 / 价值交付 / 直属部门 / 人员邮箱`。保留姓名/工号等搜索，名称、工号支持排序；姓名可筛选。按工号去重，同名不同工号仍显示为不同人员；角色列反映来源角色信息。没有成员的源角色也保留，并显示空态。

### 访问与已有数据

团队成员保留进入所属项目的入口；“团队&权限”可以只读查看。只有项目“管理角色与授权”权限或系统超级管理员可以调整功能权限、添加/编辑/删除本地角色、配置本地角色人员和部门。

已有 PMS 角色的人员、部门、权限作为本地角色保留，与 IPM 同步角色用独立身份标识区分；不因显示名称相同自动合并。同步角色的权限从模板首次初始化，不能误用旧同名本地角色的授权。已有本地角色与用户的已保存授权不做无提示清空。

IPM 成员从源角色移除后，相应同步角色权限立即失效；来源项目解绑、变更、删除、父子关系变化继续遵循现有来源校验，不复活旧 Mock 来源。同步角色是否存在由源数据决定，用户不能在 PMS 删除。

## 3. 实际权限生效规则

按以下顺序求值：

1. 固定系统超级管理员：拥有所有权限。
2. 当前项目 IPM 成员：只合并本人所属 IPM 同步角色的已保存功能权限；本地角色直接授权、部门继承与项目职责不能增加权限。
3. 非 IPM 成员：按已有本地角色的直接人员和部门继承计算有效权限。

权限主体通过工号/系统用户稳定映射识别；显示名称相同不能获得别人工号的权限。多个同步角色拥有同一功能时取并集；撤销一个角色不应覆盖另一角色仍授予的权限。

配置某项权限必须作用于对应的实际入口和写入操作。撤销后，已打开弹窗和旧回调需要在提交时重新检查当前用户、项目及该项权限。不得以“拥有任意编辑权限”统一解除所有写入限制。

保留现有计划版本、任务责任人、转维评审职责等业务约束。功能权限不会直接改变这些职责或绕过发布条件；没有可配置操作键的职责型操作仍不能靠额外角色提权。

## 4. 父子节点全选 / 取消权限

适用于全局权限中心、项目空间团队&权限，以及模板 Modal。

- 每个分类节点右侧增加“全选”“取消权限”，覆盖完整子树的全部可配置操作。
- 每个叶子菜单右侧也提供这两个操作，只影响本菜单。
- 批量按钮与分类展开按钮分开，点击授权不能同时折叠菜单。
- 搜索只定位菜单，父节点批量动作仍覆盖全部后代；通过提示明确范围，不能因筛选漏配隐藏子项。
- 一次批量操作只提交一次完整权限更新；重复出现的共享操作键先去重。
- 保留现有“编辑/导出等操作依赖查看”的归一规则，以及项目各功能现有的权限语义。
- 人员只读视图、系统超级管理员的固定全选权限、无编辑权限状态下，批量操作禁用。
- 存储失败、无权限或目标中存在不可授权的无效策略时，整次批量操作失败并保持原状态；错误可重试，不能出现只保存部分子节点的结果。

## 6. 验收

### 数据和授权

- 四类模板数据相互独立，必填、重复编码、改名、删除、刷新持久化及存储失败都覆盖。
- 初始化使用正确项目类型与角色编码；相同名字不同来源不混淆；只有首次创建复制模板；空权限与未初始化可区分。
- 模板修改、团队重复刷新不覆盖现有项目权限；源成员变更及时影响实际权限。
- 工号去重、同名不同人、多角色合并、源解绑、重新绑定、技术父子作用域、无来源项目覆盖。
- IPM 角色勾选编辑/导出实际生效；撤销即失效；本地角色和部门授予更大权限仍不能提升 IPM 成员权限；超级管理员例外。
- 新增本地角色、人员与部门配置、角色删除后权限撤销保持正确。
- 父节点全选/取消不遗漏后代，叶子操作不影响兄弟，搜索后范围一致，批量失败原子回滚，自身管理权限撤销不会留下半次更新。
- 计划、资源、转维实际操作分别校验，无权限及过期弹窗不能绕过。

### UI 与交互

- 配置中心四类入口和新全局功能权限项齐全；Modal 与项目空间表格一致。
- 项目空间只显示一个“团队&权限”，同步角色不可删，成员表字段/顺序符合图二；本地角色人员配置保持现有行为。
- 功能权限优先、角色自动选中、搜索/清空、空态、折叠及父子批量操作正常。
- 桌面和窄屏检查表格、Modal、侧栏，确保主页面不横向溢出、成员长字段可读。
- 浏览器检查新功能、旧角色配置、项目实际操作路径和 error/warn 日志。

执行新增领域/交互测试、受影响的既有测试、`npm run verify:full-regression`、`npx tsc --noEmit` 和 `npm run build`。通过后更新本地 3017 预览并提交、推送当前 `codex/feature-permission-config` 分支；不合并或部署生产。
