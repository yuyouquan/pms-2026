# PMS 转维融合实施与验收计划

> 使用 subagent-driven-development 执行独立的界面融合子任务，主任务负责模型、配置和集成；最后分别审查需求符合性和代码质量。全部验证后统一提交 feature 分支。

**目标：** 按用户四项需求，将原转维项目的流程融合到 PMS，保留 PMS 导航、项目空间及 UI 风格。

**设计：** 整机产品项目、tOS版本项目分别保存团队及模板。团队角色具有稳定 id、角色名和 IPM角色Code，发起申请时保存角色/模板快照，后续配置不改变已发起流程。角色通过 IPM code 匹配项目成员，申请中允许重新选择目录人员；SPM 角色保留终审职责。tOS 全流程只有 CheckList。沿用 Zustand，前端模拟数据不引入后端。

- [x] 模型和工作流：配置快照、动态角色、委派、逐项和批量审核、维护 SPM 终审、终止和重新发起、遗留任务变更；所有写操作复核当前用户、项目和阶段。
- [x] 配置：三级目录；CheckList 列顺序为序号、标准、类型、责任角色、资料录入-责任人、人工审核-责任人、智能检查规则；评审要素为序号、评审要素、类型、说明、备注、责任角色、资料录入-责任人、人工审核-责任人、智能检查规则。用户序号保留，连续同组的序号与标准/评审要素合并；导入、下载、导出、版本和对比均使用真实数据。
- [x] 界面：申请 modal 保持项目锁定，双列团队，计划评审日期、备注、指南；详情、录入、评审、维护 SPM 审核、关闭、重新发起。融合原项目委派、草稿、AI 模拟检查、批量评审备注、Block 和遗留任务交互。
- [x] PMS 集成：整机/tOS 申请入口、申请表格、权限、编辑离开保护、工作台待办、用户及项目切换隔离。
- [x] 验证：补充行为回归并先记录旧实现的失败；运行 typecheck、build、已有关键验证和全系统浏览器巡检，重点覆盖两类项目、动态配置、导入表头/合并、委派、驳回/重开、维护 SPM 增加/修改遗留任务及运行时错误。
- [x] 审查与交付：修复审查和测试发现，git diff --check 后提交并推送 feature；核验远端提交，保留原工作区。
