# tOS MR 与一级业务节点联动

用户确认的行为：三级计划不再单独新增 tOS 版本；一级计划上市迭代、维护阶段的业务节点决定 MR 版本的新增和删除。修订与最新发布的共享节点继续独立于发布流程维护。序号与节点名称在同一行垂直对齐。

实现：
- 读取主类型的共享业务集合；未建立集合的旧数据使用当前修订或最新发布的一级计划。缺少来源与空集合分开处理。
- 在全局订阅项目、一级计划和 MR 存储，MR 页面未打开也能同步；跨标签读取完成后再派生。
- 新节点复制最新已发布 MR 模板，一级日期未填写也生成内容，但日期编辑继续受一级日期范围与原权限约束。
- 以源节点 stableId 识别改名，保留已有活动模板和日期；删除节点则删除对应内容。
- 主类型切换保存各类型的 MR 与下游整机/市场日期，避免不同类型相同版本号互相覆盖。
- 同一源节点改名时，整机 MR 日期、转测类型、市场覆盖和行锁随源身份原子迁移；删除源节点时同步清理，随后新建同名节点不继承已删除的数据。
- 序号列预留树缩进、展开按钮及拖拽手柄宽度，并禁止换行。

验证：`verify-tos-mr-level1-sync.mjs` 覆盖增删、改名、空日期、幂等、持久化、主类型往返、同版本不同类型、跨项目隔离和 storage 事件。结合现有 MR、一级计划验证脚本、TypeScript、生产构建及浏览器实际操作验证后发布。

补充回归：`verify-mr-downstream-source-sync.mjs` 覆盖下游页面未打开时的改名、立即删除、同名重建、归档类型恢复后改名，以及整机日期、转测类型、市场覆盖和行锁的持久化。该用例先复现改名导致数据丢失，再验证原子同步修复。

跨标签回归：两个页面分别停留在新修订和已发布版本时，权限重新加载会再次执行快照初始化。`setPublishedSnapshots` 对未变化的快照必须在调用 Zustand persisted `set` 前返回，否则不同页面保留的版本选择会互相反复写入。`verify-plan-snapshot-persistence.mjs` 验证无变化时零写入、真实修改正常持久化，浏览器复测取消修订后创建新修订并检查同步是否稳定。

浏览器专项回归：`PMS_BASE_URL=http://127.0.0.1:3042 node screenshots/verify-shared-mr-linkage-browser.mjs`。使用独立浏览器 Mock 数据验证最新发布版新增、跨标签日期解锁、源改名保留下游数据、删除后同名重建、创建修订后存储写入收敛、序号居中、发布保留共享节点、刷新持久化和零运行错误；截图保存到临时证据目录。正式环境可替换 `PMS_BASE_URL` 重跑。
